# 스키마 구조 개선 점검 보고서

## ✅ 현재 구조의 장점

1. **중앙화된 관리**: 단일 소스로 스키마 관리
2. **인덱스 최적화**: 주요 조회 컬럼에 인덱스 설정
3. **트리거 활용**: updated_at 자동 업데이트
4. **JSONB 사용**: 유연한 메타데이터 저장

## ⚠️ 발견된 문제점

### 2. **데이터 타입 불일치**

#### ID 타입 불일치
```sql
-- stores 테이블
id VARCHAR(50) PRIMARY KEY

-- audio_files 테이블
store_id INTEGER  -- ❌ 타입 불일치!

-- devices 테이블  
id VARCHAR(50) PRIMARY KEY

-- audio_files 테이블
device_id INTEGER  -- ❌ 타입 불일치!
```

#### 해결 방안
- 모든 ID를 일관된 타입으로 통일 (SERIAL 또는 VARCHAR)
- 또는 외래키 관계를 명확히 정의

### 3. **외래키 관계 미정의**

```sql
-- 현재: 외래키가 없음
audio_files.store_id INTEGER
audio_files.device_id INTEGER

-- 개선: 외래키 명시
audio_files.store_id INTEGER REFERENCES stores(id)  -- 하지만 타입이 다름!
audio_files.device_id INTEGER REFERENCES devices(id)  -- 하지만 타입이 다름!
```

### 4. **누락된 필수 필드**

- `deleted_at` - 소프트 삭제를 위한 필드
- `version` - 낙관적 잠금을 위한 버전 필드
- `created_by`, `updated_by` - 감사(audit)를 위한 필드

### 5. **일관성 없는 네이밍**

- `users.id` vs `stores.id` vs `devices.id` - 일부는 SERIAL, 일부는 VARCHAR
- `created_at` vs `upload_timestamp` vs `timestamp` - 타임스탬프 필드명 불일치

## 🔧 개선 제안

### 우선순위 1: 핵심 기능 테이블 추가

```sql
-- 세션 관리
CREATE TABLE IF NOT EXISTS sessions (
    id SERIAL PRIMARY KEY,
    session_id VARCHAR(255) UNIQUE NOT NULL,
    user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
    expires_at TIMESTAMP NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 사용자 매장 접근 권한
CREATE TABLE IF NOT EXISTS user_store_access (
    user_id INTEGER REFERENCES users(id),
    store_id VARCHAR(50) REFERENCES stores(id),
    permissions JSONB,
    granted_by INTEGER REFERENCES users(id),
    granted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY (user_id, store_id)
);

-- 센서 데이터
CREATE TABLE IF NOT EXISTS sensor_readings (
    id SERIAL PRIMARY KEY,
    device_id VARCHAR(50) REFERENCES devices(id),
    timestamp TIMESTAMP NOT NULL,
    temperature DECIMAL(5, 2),
    vibration_x DECIMAL(8, 4),
    vibration_y DECIMAL(8, 4),
    vibration_z DECIMAL(8, 4),
    power_consumption DECIMAL(8, 2),
    audio_level DECIMAL(8, 4),
    sensor_quality DECIMAL(5, 2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 이상 감지
CREATE TABLE IF NOT EXISTS anomalies (
    id SERIAL PRIMARY KEY,
    device_id VARCHAR(50) REFERENCES devices(id),
    timestamp TIMESTAMP NOT NULL,
    anomaly_type VARCHAR(50) NOT NULL,
    severity VARCHAR(20) NOT NULL,
    confidence DECIMAL(5, 2) NOT NULL,
    description TEXT,
    sensor_data JSONB,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 우선순위 2: 데이터 타입 통일

**옵션 A: 모든 ID를 SERIAL로 통일 (권장)**
```sql
-- stores, devices 테이블 ID를 SERIAL로 변경
ALTER TABLE stores ALTER COLUMN id TYPE SERIAL;
ALTER TABLE devices ALTER COLUMN id TYPE SERIAL;
```

**옵션 B: 모든 ID를 VARCHAR로 통일**
```sql
-- users 테이블 ID를 VARCHAR로 변경
-- 하지만 이건 기존 데이터에 영향이 큼
```

### 우선순위 3: 외래키 관계 명확화

```sql
-- audio_files 테이블 수정
ALTER TABLE audio_files 
    ALTER COLUMN store_id TYPE VARCHAR(50),
    ALTER COLUMN device_id TYPE VARCHAR(50),
    ADD CONSTRAINT fk_audio_files_store 
        FOREIGN KEY (store_id) REFERENCES stores(id),
    ADD CONSTRAINT fk_audio_files_device 
        FOREIGN KEY (device_id) REFERENCES devices(id);
```

### 우선순위 4: 표준 필드 추가

```sql
-- 모든 테이블에 추가 권장
ALTER TABLE users ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMP;
ALTER TABLE stores ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMP;
ALTER TABLE devices ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMP;
```

## 📊 개선 여부 판단

### 현재 상태: ⚠️ 부분적 개선 필요

**잘 된 부분:**
- ✅ 중앙화된 관리 구조
- ✅ 기본 테이블 구조는 좋음
- ✅ 인덱스 최적화

**개선 필요:**
- ❌ 누락된 테이블들 (약 20개 이상)
- ❌ 데이터 타입 불일치
- ❌ 외래키 관계 미정의
- ❌ 일관성 없는 네이밍

### 권장 사항

1. **단계적 개선**
   - 1단계: 핵심 테이블 추가 (sessions, user_store_access, sensor_readings, anomalies)
   - 2단계: 데이터 타입 통일
   - 3단계: 외래키 관계 정의
   - 4단계: 나머지 테이블 추가

2. **마이그레이션 전략**
   - 각 개선 사항을 별도 마이그레이션 파일로 생성
   - 테스트 환경에서 먼저 검증
   - 프로덕션 배포 전 백업 필수

3. **문서화**
   - ERD 다이어그램 생성
   - 테이블 관계 문서화
   - 각 테이블의 용도 설명

## 결론

현재 스키마는 **기본 구조는 좋지만**, 실제 사용되는 많은 테이블들이 누락되어 있고, 데이터 타입 불일치 문제가 있습니다.

4. 전체 테이블 통합
