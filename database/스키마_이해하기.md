# 스키마가 뭐야? 쉽게 이해하기 📚

## 🎯 스키마란?

**스키마 = 데이터베이스의 설계도**

엑셀을 생각해보세요:
- **엑셀 시트** = 데이터베이스 테이블
- **엑셀의 열(컬럼)** = 데이터베이스의 필드
- **스키마** = "이 시트에는 어떤 열들이 있고, 각 열은 어떤 타입인가?"를 정의한 것

### 실생활 비유 🏠

아파트를 짓는다고 생각해보세요:
- **스키마** = 건축 설계도
- **테이블** = 아파트의 각 동
- **컬럼** = 각 동의 방 구조 (침실, 거실, 화장실 등)

설계도 없이 아파트를 짓으면? → 엉망이 됩니다!
스키마 없이 데이터베이스를 쓰면? → 데이터가 엉망이 됩니다!

## 📊 실제 예시로 이해하기

### 예시 1: 사용자 정보를 저장하는 테이블

우리 프로젝트에서 사용자 정보를 저장하려면:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,           -- 번호 (자동 증가)
    username VARCHAR(50) UNIQUE,      -- 사용자명 (최대 50자, 중복 불가)
    email VARCHAR(255) UNIQUE,        -- 이메일 (최대 255자, 중복 불가)
    password_hash VARCHAR(255),       -- 비밀번호 (암호화된 것)
    full_name VARCHAR(100),           -- 이름 (최대 100자)
    phone VARCHAR(20),                -- 전화번호 (최대 20자)
    role VARCHAR(20) DEFAULT 'user',   -- 역할 (기본값: 'user')
    created_at TIMESTAMP              -- 생성 시간
);
```

**이것이 스키마입니다!**

이 스키마는 다음을 정의합니다:
- ✅ 어떤 데이터를 저장할 수 있는지 (username, email, password 등)
- ✅ 각 데이터의 타입은 무엇인지 (문자열, 숫자, 날짜 등)
- ✅ 규칙은 무엇인지 (중복 불가, 기본값 등)

### 스키마가 없으면?

```javascript
// 스키마 없이 데이터를 저장하려고 하면?
// 어떤 필드가 있는지 모름!
// 데이터 타입이 맞는지 모름!
// 중복 체크를 어떻게 하나?

// 그래서 스키마를 먼저 정의해야 합니다!
```

## 🔍 우리 프로젝트에서의 문제점

### 문제 상황: 스키마가 여러 곳에 흩어져 있음

**1번 파일: `services/database_service.js`**
```javascript
// 여기에 users 테이블 정의
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50),
    email VARCHAR(255),
    ...
);
```

**2번 파일: `services/sqlite_database_service.js`**
```javascript
// 여기에도 users 테이블 정의 (다른 구조!)
CREATE TABLE users (
    id INTEGER PRIMARY KEY,  // ← 다름!
    username VARCHAR(50),
    email VARCHAR(100),      // ← 다름! (255 vs 100)
    ...
);
```

**3번 파일: `models/database.py`**
```python
# 여기에도 users 테이블 정의 (또 다른 구조!)
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT,              # ← 다름! (VARCHAR vs TEXT)
    password TEXT,           # ← password_hash가 아님!
    ...
);
```

### 😱 문제점

1. **일관성 없음**: 같은 테이블이 파일마다 다르게 정의됨
2. **수정 어려움**: users 테이블에 컬럼을 추가하려면 3개 파일을 모두 수정해야 함
3. **버그 발생**: 어떤 파일의 스키마가 맞는지 모름
4. **개발 속도 저하**: 매번 "어떤 파일을 수정해야 하지?" 고민

## ✅ 해결책: 중앙화된 스키마

### 변경 전 ❌
```
스키마가 3개 파일에 흩어져 있음
├── services/database_service.js
├── services/sqlite_database_service.js
└── models/database.py
```
→ 수정하려면 3개 파일을 모두 찾아서 수정해야 함

### 변경 후 ✅
```
스키마가 1개 파일에만 있음
└── database/schema.sql  ← 여기만 수정하면 됨!
```
→ 수정하려면 1개 파일만 수정하면 됨!

## 🎁 효과

### 1. 개발 속도 향상 ⚡

**변경 전:**
```
사용자 테이블에 "전화번호" 컬럼 추가하려면?
1. database_service.js 찾기
2. sqlite_database_service.js 찾기  
3. database.py 찾기
4. 3개 파일 모두 수정
5. 실수로 1개 파일을 놓쳤는지 확인
6. 테스트
→ 시간: 30분
```

**변경 후:**
```
사용자 테이블에 "전화번호" 컬럼 추가하려면?
1. database/schema.sql 열기
2. phone 컬럼 추가
3. 테스트
→ 시간: 5분
```

### 2. 버그 방지 🐛

**변경 전:**
- 파일 A: email을 VARCHAR(255)로 정의
- 파일 B: email을 VARCHAR(100)으로 정의
- → 이메일이 200자면? 파일 B에서 에러!

**변경 후:**
- 모든 파일이 같은 스키마 사용
- → 일관성 보장!

### 3. 협업 용이 🤝

**변경 전:**
```
개발자 A: "users 테이블에 뭐가 있지?"
→ 3개 파일을 모두 확인해야 함
→ 시간 낭비 😫
```

**변경 후:**
```
개발자 A: "users 테이블에 뭐가 있지?"
→ database/schema.sql만 열면 됨
→ 5초 만에 확인! 😊
```

## 📝 실제 사용 예시

### 사용자 테이블에 "생년월일" 필드 추가하기

**1단계: 스키마 파일 열기**
```bash
# database/schema.sql 파일 열기
```

**2단계: 스키마 수정**
```sql
-- database/schema.sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(100),
    phone VARCHAR(20),
    birth_date DATE,  -- ← 여기 추가!
    role VARCHAR(20) DEFAULT 'user',
    ...
);
```

**3단계: 완료!**
- 다른 코드는 자동으로 이 스키마를 사용합니다
- 별도 수정 불필요!

## 🎯 핵심 정리

### 스키마 = 데이터베이스 설계도

1. **무엇을 저장할지** 정의 (컬럼 이름)
2. **어떤 타입인지** 정의 (문자열, 숫자, 날짜 등)
3. **어떤 규칙인지** 정의 (중복 불가, 필수 입력 등)

### 왜 중요해?

1. **일관성**: 모든 코드가 같은 구조 사용
2. **효율성**: 한 곳만 수정하면 됨
3. **명확성**: "어디에 뭐가 있나?" 바로 확인
4. **안정성**: 버그 발생 가능성 감소

### 우리가 한 일

**Before (이전):**
```
스키마가 여러 파일에 흩어져 있음
→ 수정하려면 여러 파일 찾아야 함
→ 실수하기 쉬움
→ 개발 속도 느림
```

**After (현재):**
```
스키마가 database/schema.sql 한 곳에만 있음
→ 수정하려면 한 파일만 수정
→ 실수 없음
→ 개발 속도 빠름
```
